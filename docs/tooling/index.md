These pages describe the mechanics: how Liara is built, tested, validated, packaged and published. For the reasoning behind the choices, the records in [Architecture decision records](../adr/) carry it. For what a working day looks like, [`contributing.md`](../contributing/) does.

## Adding a tool

The tools listed above are the only ones in use, and introducing another one requires a record in [Architecture decision records](../adr/). The single exception is the bootstrapping phase, whose policy is in [`roadmap.md`](../roadmap/) §4.

Zig and Rust are optional on a developer machine, since the cross-language tests are registered only when `find_program` locates a toolchain and are silently absent otherwise. They are not optional in CI, where one matrix leg fails configuration without them.

## What is deliberately absent

Each of these is a decision rather than an oversight.

- **No Conan.** vcpkg fills the role, for the reasons in [ADR 0007](../adr/0007-cmake-presets-and-vcpkg/).
- **No Bazel, Meson or premake.** CMake is enough, and the ecosystem argument is in the same record.
- **No Husky, and no pre-commit hook framework.** CI is the gatekeeper, and `./scripts/liara.sh check` runs the same checks locally for anyone who wants them earlier.
- **No Jenkins, GitLab CI or CircleCI.** GitHub Actions is where the code already lives.
- **No proprietary analysis tooling** beyond what SonarCloud's free tier offers.
- **No package signing.** Deferred until something is actually distributed to somebody.
- **No Docker at runtime.** The engine is not containerized. The only image in the project builds
  documentation.
