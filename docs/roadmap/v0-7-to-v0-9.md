These three versions introduce no major feature. They exist to use the engine to build something and fix the friction that turns up. Each version is one iteration: build part of a small game, file down the rough edges, improve the documentation.

This is the phase where most hobby engine projects fail, by skipping it. An engine that has not been used to build a game cannot be claimed to be usable for building games, and every version before this one is a claim.

## What gets built

A small but complete 3D game. Not a tech demo. The suggested archetype is a corridor or a small explorable scene where the player walks around, interacts with objects, triggers events and reaches an end state: concrete enough to ship, simple enough to finish.

The choice of game is not prescribed, and the criteria are. It has to exercise mesh rendering, lighting, input, audio and asset loading. It has to have a beginning and an end. It has to be packageable. The rule of thumb: the smallest thing somebody unrelated to the project would call a game rather than a demo.

## The iteration

Each of v0.7, v0.8 and v0.9 runs the same loop.

1. Find the next set of frictions.
2. Fix them in the engine, not in the game.
3. Document the fixes.
4. Update the sample game to use the improved APIs.
5. Tag the version.

Step 1 has a constraint that does the real work: frictions are discovered by genuinely trying to build the game. A hypothetical friction is out of scope, and if it does not actually hurt while building, it does not get fixed here.

## Definition of Done for the phase

The public engine APIs are two things. For a game written in C++, they are `Liara::Framework`, the convenience layer described in [liara-framework](../../modules/framework/). For a game written in anything else, they are the C ABI declared in `liara-interfaces`, called directly. The framework is the intended path and the sample game takes it; the ABI stays available underneath, since the framework adds no capability the contract does not already carry.

- [ ] A small 3D game has been built using only the public engine APIs.
- [ ] It is shippable: a start, an end, sounds, lights and a few interactive elements.
- [ ] It is packaged and runs from both the Linux and the Windows distribution.
- [ ] Every friction found has been either fixed or recorded as known and deferred.
- [ ] The user documentation has at least one real tutorial taking somebody from an empty project to a small game.
