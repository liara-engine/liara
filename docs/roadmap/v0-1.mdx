The first real version. The goal is not to render something impressive, it is to prove the modular pipeline works end to end. Every architectural decision gets exercised at once: the C interfaces, the host's composition and version negotiation, the renderer's Vulkan initialisation, the launcher wiring core and renderer together, the cross-platform build.

If v0.1 ships, the hardest architectural risk is behind the project and every version after it is "just" adding features.

## Scope

The launcher initializes the platform, the core and the renderer independently through the C interface, checks their ABI versions against each other, and composes them. It creates a window through the platform module, passes its native handle to the renderer, drives the core's per-tick step, and carries the render packets the core produces across to the renderer, which draws one hardcoded triangle and presents it.

The window's close button and a Ctrl+C surface as the same shutdown request from the platform module, and both produce the same graceful shutdown.

The triangle is hardcoded in the launcher: three vertices, a vertex shader, a fragment shader. No ECS, no asset loader, no math beyond what the renderer needs internally.

The renderer initializes Vulkan with validation layers on in debug builds, using Vulkan-Hpp for type safety and VMA for memory.

## Out of scope

The ECS (v0.2), asset loading (v0.3), lighting (v0.4), input beyond the window closing and audio (v0.5), several objects, frames whose content differs, configurable shaders, and anything resembling an editor.

## Definition of Done

- [ ] The launcher builds and runs on Linux, under GCC and Clang.
- [ ] The launcher builds and runs on Windows, under MSVC.
- [ ] A window appears with a triangle in it.
- [ ] The window closes and the application shuts down cleanly.
- [ ] No Vulkan validation errors in debug builds.
- [ ] Version negotiation between core and renderer is exercised: a mismatch is detected before anything is called, produces a clear error and refuses to proceed, with no crash and no silent mismatch. Under the `-runtime` presets the same check runs after symbol resolution rather than before the first call, and both paths reach the same verdict.
- [ ] Tests pass on every platform.
- [ ] The user documentation has a "Build hello triangle" page.
- [ ] The compatibility record is updated.
- [ ] The v1 manifest schema is retired: no manifest declares it, and a new one that did would not pass validation. Reading v1 stays, for old-tag rebuilds.
- [ ] `liara-platform` exists, is released, and appears in it.
- [ ] Closing the window and sending SIGINT produce the same clean shutdown path.

## The composition tool <Badge text="Experimental" variant="caution" />

Not a milestone of its own. It is a developer tool that becomes useful the moment more than one module has independently moving versions, which is as soon as v0.1 ships, and it is introduced here in a deliberately minimal form.

### Why

Modules version independently, so the question "does core 0.2 still work against renderer 0.1?" stops being answerable by reading and starts needing to be run. Rebuilding every combination from source to find out is slow, and publishing shared-library artefacts exists precisely so that a combination can be assembled from precompiled binaries in seconds.

### Scope

A script in the meta repository's `scripts/` that takes a set of module versions, downloads the matching release artifacts, validates the combination against each module's `manifest.json`, assembles them into a runnable layout next to the launcher, and reports whether the combination is ABI-consistent before anything runs.

It reads the same manifests the documentation switchers already consume, which is what makes those manifests the single machine-readable source of truth for compatibility, and is why there is no separate compatibility file. [ADR 0006](../../adr/0006-manifest-as-compatibility-source-of-truth/) records that.

This form is for me. It is allowed to be rough: a command-line tool, minimal error prettiness, Linux first.

### Out of scope

User-facing polish, meaning interactive selection, friendly diagnostics and a curated catalogue of known-good sets. Producing a distributable package from a composed set, which is packaging and belongs to v0.6. Windows parity beyond running at all.

### Definition of Done

- [ ] Given explicit module versions, it fetches the matching artifacts and manifests.
- [ ] It rejects an ABI-incompatible combination with a clear message, before assembly.
- [ ] It assembles a compatible combination into a layout the launcher can run against.
- [ ] It works on Linux for my own workflow.

## The module loader

Also not a milestone. It is the piece of the host that turns "the interfaces are designed as if modules were dynamic" into something a program actually runs.

It carried an `Experimental` badge until the loader was built. It no longer does: `-runtime` is the only way to load a module this build system did not build, so it is the production path for any module not written in C or C++, and [ADR 0012](../../adr/0012-generated-module-dispatch-tables/) records its shape.

### Why

[Modularity model](../../architecture/modularity/) claims that switching to runtime loading is a matter of writing a loader rather than rewriting contracts. A claim nothing exercises is a claim nobody has checked. The `-runtime` presets exist from Phase 0 precisely so the claim is testable early, before enough code has accumulated for a static coupling to be expensive to undo.

### Scope

The launcher gains a small loader. It resolves each module's shared library by a platform-correct name, opens it, resolves that module's `liara_<module>_info` entry point plus the handful of functions the host actually calls, runs the negotiation of [ADR 0005](../../adr/0005-version-encoding-and-compatibility/) on the result, and refuses to proceed on `INCOMPATIBLE`. Library names live in one place, next to the platform macros, rather than being spelled at each call site.

In this form it is deliberately naive: a fixed list of modules, no discovery, no plugin directory, no versioned filename resolution, no graceful degradation when a module is absent.

### Out of scope

Module discovery, meaning scanning a directory, reading a manifest and deciding what to load. Loading a module the launcher was not compiled to know about. Unload and reload at run time, which is code hot-reload and deferred indefinitely. Any policy beyond refusing `INCOMPATIBLE` and warning on `DEGRADED`.

### Definition of Done

- [x] Under the `-runtime` presets, the launcher links against `liara-interfaces` only, and the module libraries are resolved at load time.
- [ ] Library names are correct on Linux and Windows, and defined in one place.
- [x] A contrived ABI mismatch is detected after symbol resolution and refuses to proceed, with a message naming the module and both versions.
- [x] A missing or unopenable library produces a clear error rather than a crash.
- [x] The `-runtime` presets are exercised by CI on both platforms.
